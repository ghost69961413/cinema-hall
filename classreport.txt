2. ABSTRACT
-------------------------------------------------------------------------------
Cinema ticket booking must prevent two customers from booking one seat and must
free seats when a customer does not complete payment. This project provides a
web-based cinema booking system backed by PostgreSQL functions on Supabase.
The database stores show-specific seat states, applies temporary holds, records
payments, and releases expired holds. A browser-based concurrency simulation
and the supplied test script demonstrate that concurrent attempts cannot both
claim the same seat. The project also includes customer authentication, live
seat updates, and an administrator dashboard.

3. INTRODUCTION AND PROBLEM STATEMENT
-------------------------------------------------------------------------------
Paper-based and simple online booking can let two customers select one seat at
the same time. A customer may also select seats and leave before paying, which
can keep seats unavailable to others. Customers need current seat information
while other bookings change the seating plan.

This project represents every seat for every show in a show_seats table. A
database function locks requested seat rows and creates a temporary five-minute
hold as one transaction. Successful payment changes the seats to booked. An
expiry function returns unpaid seats to available. Supabase Realtime and the
frontend refresh logic communicate state changes to the interface.

4. OBJECTIVES
-------------------------------------------------------------------------------
- Store movies, screens, seats, shows, bookings, payments, and profiles.
- Prevent concurrent customers from claiming the same seat.
- Hold seats temporarily while a customer completes checkout.
- Record a confirmed booking and payment in the database.
- Return expired, unpaid seats to the available state.
- Show seat availability and booking information to customers and admins.
- Restrict customer and administrator data access with Row Level Security.

7. SYSTEM ARCHITECTURE
-------------------------------------------------------------------------------
The browser loads the static HTML, CSS, and JavaScript files. The application
uses Supabase Auth for sessions and calls PostgreSQL functions through Supabase
RPC for protected booking operations. PostgreSQL stores the catalog, seats,
bookings, and payments. Row Level Security policies limit database access.
Realtime sends published table changes to connected browsers. pg_cron runs the
expired-hold function every minute. If Supabase configuration is unavailable,
the app includes an in-memory demonstration mode; serve.py also provides a
local mock database endpoint.

  Customer/Admin browser
       | Auth, database reads, RPC calls
       v
  Supabase Auth ---- PostgreSQL tables and functions
                          |             |
                          |             +--- pg_cron expiry sweep
                          +--- Realtime publication --> connected browsers

8. DATABASE DESIGN
-------------------------------------------------------------------------------
The following design is read from sql/01_schema.sql. UUID primary keys are
generated with gen_random_uuid() where a default is defined. Profile IDs come
from Supabase Auth.

TABLE: profiles
  id uuid PRIMARY KEY, references auth.users(id) ON DELETE CASCADE
  full_name text NOT NULL
  role text NOT NULL DEFAULT 'customer', CHECK role is customer or admin
  created_at timestamptz NOT NULL DEFAULT now()

TABLE: movies
  id uuid PRIMARY KEY DEFAULT gen_random_uuid()
  title text NOT NULL; language text NOT NULL
  duration_min int NOT NULL, CHECK duration_min > 0
  genre text; rating text DEFAULT 'UA'; poster_url text; synopsis text
  created_at timestamptz NOT NULL DEFAULT now()

TABLE: screens
  id uuid PRIMARY KEY DEFAULT gen_random_uuid()
  name text NOT NULL UNIQUE
  screen_type text DEFAULT 'Standard'

TABLE: seats
  id uuid PRIMARY KEY DEFAULT gen_random_uuid()
  screen_id uuid NOT NULL, FK screens(id) ON DELETE CASCADE
  row_label text NOT NULL; seat_number int NOT NULL
  tier text DEFAULT 'Standard'
  UNIQUE (screen_id, row_label, seat_number)

TABLE: shows
  id uuid PRIMARY KEY DEFAULT gen_random_uuid()
  movie_id uuid NOT NULL, FK movies(id) ON DELETE CASCADE
  screen_id uuid NOT NULL, FK screens(id) ON DELETE CASCADE
  starts_at timestamptz NOT NULL
  ticket_price numeric(8,2) NOT NULL, CHECK ticket_price > 0
  UNIQUE (screen_id, starts_at)

TABLE: bookings
  id uuid PRIMARY KEY DEFAULT gen_random_uuid()
  user_id uuid NOT NULL, FK profiles(id) ON DELETE CASCADE
  show_id uuid NOT NULL, FK shows(id) ON DELETE CASCADE
  status booking_status NOT NULL DEFAULT 'pending'
  total_amount numeric(10,2) NOT NULL, CHECK total_amount >= 0
  expires_at timestamptz NOT NULL
  created_at timestamptz NOT NULL DEFAULT now()

TABLE: show_seats
  show_id uuid NOT NULL, FK shows(id) ON DELETE CASCADE
  seat_id uuid NOT NULL, FK seats(id) ON DELETE CASCADE
  status seat_status NOT NULL DEFAULT 'available'
  booking_id uuid, FK bookings(id) ON DELETE SET NULL
  hold_expires_at timestamptz
  PRIMARY KEY (show_id, seat_id)
  CHECK status = available OR booking_id IS NOT NULL
  CHECK status is not held OR hold_expires_at IS NOT NULL

TABLE: payments
  id uuid PRIMARY KEY DEFAULT gen_random_uuid()
  booking_id uuid NOT NULL UNIQUE, FK bookings(id) ON DELETE CASCADE
  amount numeric(10,2) NOT NULL, CHECK amount >= 0
  paid_at timestamptz NOT NULL DEFAULT now()

RELATIONSHIPS
  - One profile can have many bookings.
  - One movie can have many shows; one screen can host many shows.
  - One screen has many physical seats.
  - One show has one show_seats row for each physical seat on its screen.
  - A booking can be linked from multiple show_seats rows.
  - A booking has at most one payment, enforced by UNIQUE payments.booking_id.

ENUMS, INDEXES, VIEWS, AND SECURITY
  seat_status: available, held, booked.
  booking_status: pending, confirmed, expired.
  Indexes: idx_show_seats_held (hold_expires_at) WHERE status = 'held';
  idx_shows_starts_at (starts_at); idx_bookings_user_id (user_id);
  idx_seats_screen (screen_id).
  No CREATE VIEW statement appears in the project SQL. Admin data is returned
  by the admin_show_data RPC function instead.
  RLS is enabled for profiles, movies, screens, seats, shows, show_seats,
  bookings, and payments. Policies are defined in sql/03_rls.sql. Admins can
  read all profiles, bookings, show seats, and payments; manage screens; and
  insert movies and shows in the admin SQL. Customers can read public catalog
  data and their own bookings/payments. Direct booking writes are restricted
  and booking operations use database functions.

SEAT STATE TRANSITIONS
  available -> held: successful hold_seats call; expiration is five minutes.
  held -> booked: successful pay_booking call before expiry.
  held -> available: release_expired_holds after expiry, or a later seat-map
                    read triggers an expiry sweep.

  ER DIAGRAM
  auth.users 1---1 profiles 1---many bookings 1---0..1 payments
  movies 1---many shows many---1 screens 1---many seats
  shows 1---many show_seats many---1 seats
  bookings 1---many show_seats

9. CORE DATABASE LOGIC
-------------------------------------------------------------------------------
All definitions below are in sql/01_schema.sql and sql/02_functions.sql.
The hold and payment changes run within the database transaction that executes
each function. Row locks and conditional updates protect shared seat rows.

FUNCTION: is_admin()
  Checks whether the authenticated profile has role 'admin'. SECURITY DEFINER
  allows the function to read the role despite profile RLS.

  create or replace function public.is_admin()
  returns boolean language sql security definer
  set search_path = public, pg_temp as $$
    select exists (
      select 1 from public.profiles
      where id = auth.uid() and role = 'admin'
    );
  $$;

FUNCTION: hold_seats(p_show_id uuid, p_seat_ids uuid[])
  Requires a signed-in user and between one and six distinct seats. It locks
  show_seats rows ordered by seat_id with SELECT FOR UPDATE. It creates a
  pending booking with a five-minute expiry, then conditionally updates only
  available or expired-held rows. If it cannot update every requested row, it
  raises an exception; PostgreSQL rolls back the transaction. Fixed lock order
  reduces deadlock risk. Core SQL:

  perform 1 from show_seats
   where show_id = p_show_id and seat_id = any(p_seat_ids)
   order by seat_id for update;
  insert into bookings (user_id, show_id, total_amount, expires_at)
  values (v_user_id, p_show_id, v_price * cardinality(p_seat_ids),
          now() + interval '5 minutes') returning id into v_booking;
  update show_seats
     set status = 'held', booking_id = v_booking,
         hold_expires_at = now() + interval '5 minutes'
   where show_id = p_show_id and seat_id = any(p_seat_ids)
     and (status = 'available' or
          (status = 'held' and hold_expires_at < now()));
  get diagnostics v_updated = row_count;
  if v_updated <> cardinality(p_seat_ids) then
    raise exception 'Someone just took one of these seats';
  end if;

FUNCTION: pay_booking(p_booking_id uuid)
  Locks the current user's unexpired pending booking. It confirms that held
  seats still exist, changes them to booked, creates one payment row, and marks
  the booking confirmed. Row-count validation raises an error if the hold
  changed before the transaction could complete.

  select total_amount into v_amount from bookings
   where id = p_booking_id and user_id = v_user_id
     and status = 'pending' and expires_at > now() for update;
  if not found then raise exception 'Booking expired or not found'; end if;
  select count(*) into v_seats from show_seats
   where booking_id = p_booking_id and status = 'held'
     and hold_expires_at > now();
  update show_seats set status = 'booked', hold_expires_at = null
   where booking_id = p_booking_id and status = 'held'
     and hold_expires_at > now();
  get diagnostics v_booked = row_count;
  if v_booked <> v_seats then
    raise exception 'Seats are no longer held';
  end if;
  insert into payments (booking_id, amount) values (p_booking_id, v_amount);
  update bookings set status = 'confirmed' where id = p_booking_id;

FUNCTION: release_expired_holds()
  Changes expired held seats to available and marks expired pending bookings
  as expired. It returns the number of released seats. pg_cron schedules it
  each minute using the expression '* * * * *'.

  update show_seats
     set status = 'available', booking_id = null, hold_expires_at = null
   where status = 'held' and hold_expires_at < now();
  get diagnostics v_count = row_count;
  update bookings set status = 'expired'
   where status = 'pending' and expires_at < now();
  return v_count;

FUNCTION: get_show_seat_map(p_show_id uuid)
  Calls release_expired_holds before returning seat ID, row, number, tier,
  status, hold expiry, and whether the current user owns the hold. This keeps
  an expired hold from continuing to appear occupied when the seat map loads.

FUNCTION: admin_show_data(p_show_id uuid)
  Requires is_admin(). Returns show and screen details, total/booked/held/
  available counts, booking count, confirmed-payment sum, booked-seat records,
  and unexpired held-seat records as JSON. It joins seats, bookings, profiles,
  auth users, and payments for the dashboard data.

FUNCTION: get_booking_details(p_booking_id uuid)
  Returns a JSON booking summary, show/movie/screen information, seats, and
  payment for the booking that belongs to auth.uid().

TRIGGER FUNCTIONS
  handle_new_user() inserts or updates profiles when a row is added to
  auth.users. populate_show_seats() adds available show_seats rows for the
  seats on a newly inserted show. Both are PL/pgSQL trigger functions in
  sql/01_schema.sql. The full function bodies are in that file.

10. HOW DOUBLE BOOKING IS PREVENTED
-------------------------------------------------------------------------------
1. Each user sends a hold request for a show and one or more seat IDs.
2. hold_seats verifies authentication and the requested seat count.
3. PostgreSQL locks the selected rows in show_id and seat_id order.
4. The function updates only available or expired-held rows.
5. If another transaction holds a requested row first, the conditional update
   cannot update every row and the function raises an exception.
6. That exception rolls the entire transaction back, including its booking row.
7. The successful transaction leaves the seat held for five minutes; a second
   user cannot successfully hold it during that interval.
